# Reconcile source and app records

Reconcile a named period on the basis the user selected. Keep source completeness, balance agreement, transaction classification, cross-account matching and native linking as separate outcomes. An app-only result can prove app consistency but cannot prove bank completeness. This workflow does not replace ordinary transaction review; use [along-review-transactions](../along-review-transactions/SKILL.md) for categories, receipts, splits, assignments, reviewed state and rule previews.

## Choose the route before work

Resolve enough household/app identity to choose one route. Do not invoke setup automatically.

| Route | Use when | Basis and result |
| --- | --- | --- |
| **Along source** | `feedOwner=along` and handoff is verified | Use basis `along-source`: reuse or retrieve fresh-enough source evidence through the saved connection, then compare it with the app. Reconcile and apply only explicitly authorized fixes; never trigger routine sync/import. |
| **App only** | The account is non-onboarded, app-managed, manual or has no verified Along handoff, and no source file was supplied | Use basis `app-only`: inspect app rows, split parent/children, internal transfers and candidate duplicates. Lead with “app ledger reviewed”; state source coverage as unknown and source reconciliation as not performed. Do not headline the result as reconciled or balance verified. |
| **Provided source** | The user supplies statements or exports | Use basis `provided-source`: compare the supplied source to the app for the named scope without onboarding. Source-backed repairs may follow the changes contract when separately authorized; no routine sync/import is implied. |
| **One-off source** | The user explicitly requests a source comparison without onboarding and supplies or authorizes the needed source route | Use basis `one-off-source`: compare only the named scope without creating persistent onboarding. Source-backed repairs may follow the changes contract when separately authorized; no routine sync/import is implied. |
| **Setup** | The user explicitly asks to create or change the Along household profile, app/workspace, storage or access route | Route to the explicit Along setup command; reconcile never initializes setup. |
| **Other request** | The user asks to onboard, connect, switch feeds, perform a routine bank-to-app update, or show account status/health | Route onboarding or routine updates to `along-sync-account`; route status to the separate status workflow. Reconcile does not create connectors, switch feed ownership or perform status-only work. |

If the request could mean app-only inspection, one-off source comparison or onboarding/routine sync, ask the user to choose. A specifically named or supplied statement/export takes precedence over the Along-source route, even when `feedOwner=along`: use **Provided source**, compare those files, and do not retrieve fresher source evidence. A supplied statement/export never forces onboarding. If no household profile exists, do not invoke setup from this skill; ask the user to invoke the explicit Along setup command for persistent source onboarding, while continuing any independent app-only or supplied-file inspection that does not need it.

Read [workflow](../along-sync-account/references/workflow.md) for every run; [records](../along-sync-account/references/records.md) when reading or saving household evidence/cases; [capabilities](../along-sync-account/references/capabilities.md) before interpreting unfamiliar app behavior; and [changes](../along-sync-account/references/changes.md) before proposing or applying app changes. Read [evidence](../along-sync-account/references/evidence.md) before acquiring or interpreting statements/exports, [authentication](../along-sync-account/references/authentication.md) before new source access, and [Monarch knowledge](../along-sync-account/references/monarch.md) when app semantics matter. Read [movement checks](references/movements.md) for any payroll, transfer, wallet, card, loan, lease, brokerage or refund flow. A cross-flow visual is optional and belongs to [along-report-money](../along-report-money/SKILL.md); it is never a completion requirement for a narrow discrepancy check.

## Reconciliation loop

1. **Bound the run.** Resolve the household, app workspace, accounts, route, currency, timezone, period, as-of point and mode. Use an explicit period unchanged. Otherwise use the selected/latest complete statement period or resume after verified coverage; for app-only work with no checkpoint, use the latest complete calendar month. State exact dates, and read adjacent dates only as settlement context. “Reconcile” defaults to `inspect`; a requested repair can produce `prepare`, and a precise request naming the exact row and approved operation can authorize `apply` under the changes contract. Do not silently default to year-to-date.

2. **Build the account map.** Count each physical account once while retaining every app mapping. Record owner, institution, masked identity, account type, currency, app coverage, source coverage when available, feed owner, handoff state and balance definition. For the Along-source route, verify the saved connection and mapping; for app-only work, do not infer a bank identity or onboarding from the app login. Include in-scope unmapped, closed, inaccessible and balance-only accounts as explicit findings. Map source rows to app rows, pending-to-posted replacements, split parents and allocation children; parent-child identity is a relationship and is not required to preserve one row ID.

3. **Establish evidence coverage.** Branch by route. For **Along source**, reuse or retrieve source evidence through the verified saved connection when it is fresh enough for the requested period/as-of; do not refresh the app connector, import transactions or change feed ownership just to reconcile. If access is expired or blocked, report the gap and offer the scoped recovery action through sync-account; do not silently reauthenticate or change connections. Adequate saved evidence can still support independent comparisons. For **Provided source**, validate the supplied statement/export and its actual coverage without onboarding. For **One-off source**, use only the explicitly authorized source route to retrieve the named scope, or the supplied evidence if available; do not establish persistent onboarding. For **App only**, do not fetch source evidence; record source completeness as unavailable and continue the app checks. In source routes, reuse an immutable evidence bundle only when its identity, period, pending/posted treatment and as-of fit the run; preserve source IDs when available, otherwise use the source fingerprint, signed integer minor-unit amount, currency, original description, dates, status and duplicate ordinal. Validate the normalized fields needed for each match or correction against their source provenance; unresolved identity, amount/sign, currency or dates block dependent conclusions and writes, not independent comparisons. Treat missing evidence as a finding, never as zero activity.

4. **Compare and classify records.** In **App only**, inspect app internal consistency, signed amounts/dates, split conservation, existing transfer/payment pairs and candidate duplicates; a candidate missing row or duplicate remains unproven without source evidence. In either source route, search both directions and inspect overlaps before declaring a row missing or duplicated. Classify each source/app relationship as matched, missing from app, missing from source evidence, timing difference, pending replacement, conflicting, candidate duplicate, ambiguous, unsupported or intentionally out of scope. Equal amount or merchant text alone proves neither identity nor duplication. Compare balances only at aligned dates with compatible current/available/statement or principal/valuation definitions; a matching balance does not prove transaction completeness. For pending activity in scope, record still pending, replaced by posted, source-confirmed reversed/expired, or unresolved, with evidence and next action. If requested current-cycle pending coverage is unavailable, that result stays partial. A complete posted-only comparison must explicitly exclude pending coverage.

5. **Recover only proven exceptions.** In **App only**, report candidate missing/duplicate cases and continue independent checks; do not present an app anomaly as a source-backed repair. In either source route, a connected account does not require feed takeover for a bounded repair. For a missing row, require source proof, exact account and signed date/amount/currency, a search for pending, posted, manual, imported and split alternatives, an observed app operation that can create the row, and a duplicate guard. For a true duplicate, require source/app identity evidence, inspection of replacement and split relationships, and a precisely named row and operation. Prepare the before/after, source references, duplicate search, possible later redelivery and recovery path. Apply only the fixed approved change; never run broad deduplication, trigger a routine import or create a balancing plug. If capability or identity remains uncertain, report/propose only.

6. **Check household movements.** For app-only work, map only existing app-side transfers/payments and candidate counterparts, clearly labeling that the map cannot prove bank completeness. For a requested cross-account inspection or a counterpart needed to resolve a selected source discrepancy, build a scoped map with origin, destination, purpose, observed legs, settlement window, coverage, match basis, confidence, native-link state and unresolved work. Use [movement checks](references/movements.md) for payroll routing and benefits, internal transfers, wallets, card payments, loans, leases, brokerage cash and refunds. Match one-to-one unless source evidence supports a grouped allocation. Preserve each source date and do not invent a counterpart to make totals balance. Distinguish an evidence match from a native app link; a link that changes dates, creates rows or alters exclusions needs its own capability and approval check.

7. **Apply and verify.** Use the shared single-writer, before-snapshot, drift check, journal and reread protocol. For the Along-source route, apply only the exact authorized reconciliation fix; do not sync, import, switch feeds or create a connector. For the app-only route, any separately authorized app-local metadata changes belong to transaction review; creation/deletion, amount/date/account changes, and missing/duplicate repairs require a source-backed route. App observations alone cannot authorize ledger reconstruction. Reopen every repaired or linked row, its parent/children and affected balances. Verify source identity or fingerprint when source-backed, signed amount, currency, date, account, count effects, split conservation and native-link state. If a save is uncertain, inspect before retrying. A missing-row repair remains a tracked later-duplicate case until the relevant feed interval has been observed; persist that case and do not copy the transaction into Along's records.

8. **Persist and report.** Save the run with basis `app-only`, `provided-source`, `one-off-source` or `along-source`, plus the account map, evidence references, pair/movement references, proposal and journal references, cursor/checkpoint, later-duplicate cases and residuals under the private records contract. Preserve prior observations and user exclusions; store references rather than a second ledger. Report source coverage, app coverage, matched/missing/ambiguous/duplicate counts, balance result, movement result, native-link result, repairs verified/unapplied/unknown and remaining evidence separately. Label each result as app-observed, saved-connection source, supplied-source, user-provided or inferred, and list the checks actually verified with their evidence/as-of. For `app-only`, lead with “app ledger reviewed,” state “source coverage: unknown” and “source reconciliation: not performed,” and do not headline “reconciled” or “balance verified.” `complete` applies only to the named checks and covered period; an app-only run cannot claim bank completeness, and any unsupported or unresolved result is visible in the outcome.


## Household period reconciliation

For an explicit household-wide reconciliation or close request, choose the route first, define the included accounts and required checks, reuse adequate account-period results, then perform the scoped cross-account checks above. An app-only household result remains app-basis and cannot prove source completeness. Store one household run index under `reconciliations/<runId>/` referencing account evidence and unresolved cases. Report the aggregate as partial when any required account/check lacks evidence or remains unresolved; do not promote a healthy balance or a completed report to a verified household close. A requested budget/goal close belongs to `along-manage-budget` and does not implicitly request this broader audit.
