# Authorize, apply and recover

All Along writers use this contract and the operation boundaries in [workflow](workflow.md). Keep **inspect** (findings), **prepare** (reviewable changes), and **apply** (authorized changes plus verification) distinct. Interpret legacy `validate` as inspect without rewriting old records.

## Match authorization to the actual action

Read-only requests remain read-only. An explicit instruction identifying the records, values and effects can authorize that exact operation; record the user-message reference and do not ask again. “Mark these three confirmed purchases reviewed” differs from “review my finances.” Broad “fix/categorize/reconcile” requests authorize investigation and preparation but need a concrete batch when the agent must choose material values, deletions, allocations or future rule behavior. Existing approval for the same unchanged proposal remains valid. A preference or setup consent is not a financial-write mandate. For routine Along sync, a separately recorded bounded import authorization can cover deterministic source-backed additions to named accounts within its allowed period/baseline and operation policy. Check that authorization against the current batch; new inferred values, destructive import modes, deletions or changed effects need a concrete proposal. Account onboarding or a requested cadence alone is not that authorization.

Before asking, finish the proposal: stable change IDs, target identities, current and proposed values, evidence/reason, unresolved choices, affected period/accounts/counterparts, expected counts/balance/report/review effects, and recovery options. Separate optional rule creation from one-time correction and permit partial approval. For directly authorized operations, record the same before/after plan internally before writing. Bind authorization to a proposal version/digest or the equivalent exact request; changed material effects need authorization only for those changes.

For a duplicate-removal proposal, identify the row to keep and the row to remove, the evidence for duplication, retained categories/notes/splits/links, count and balance effects, and any metadata reconciliation needed. Present that plan for approval when the request has not already specified those exact choices and effects; approval to delete one row does not authorize losing unrelated information or choosing another survivor.

Native action names do not define safety. Inspect [capabilities](capabilities.md): a split can replace rows and mark them reviewed; a goal link can remove spending from budget actuals; merchant edits may affect recurring items; an import may delete a whole date range. Preserve a traceable source-to-app mapping and conserved financial totals under the observed app model. Unsupported or unknown behavior stays proposed.

## Execute once and verify

1. Use established private storage (missing household configuration follows the explicit setup boundary in workflow) and establish exclusive execution ownership for the affected household/account set, through a real supported lock or a single verified active writer. Registry updates require serialization and atomic replacement too. If exclusivity is unknown, prepare only; a timeout is not proof the old writer stopped.
2. Save an available export/backup or focused before-snapshot. Explain any limits to restoration. Re-read identity, current values, feed state and relevant settings just before writing. Stop the affected changes on drift rather than overwriting newer user/app edits.
3. Persist each operation as `planned → authorized → started → applied-unverified → verified`, or `blocked/failed/unknown`, with an operation key and evidence. Read legacy `approved` as authorization with its original provenance. Persist `started` before the external save; journal rejected/skipped changes too.
4. Apply through supported controls or an actually authorized connector with known semantics. For imports record mode, exact row/date/account scope, duplicate policy, ID mapping and expected effects. A small live test is still a write requiring authorization. Stop on unpredictable batch effects.
5. Reopen/re-read the resulting records and affected views. Verify actual values, parent/child identity mapping, split totals, source relationships, counts, review state, counterparts and balances as applicable. A dialog closing or import starting is not completion. Poll an actual pending operation only within tool limits; keep it unverified until completed and inspected.

After an uncertain save, inspect by IDs, before/after values, fingerprints and count effects before retrying. Presence or amount alone is insufficient. A missing external ID need not block verification when alternative evidence uniquely establishes the result. An ambiguous outcome remains unknown and blocks dependent writes; never repeat an import/creation/split blindly.

## Targeted recovery and later changes

For a missing transaction on a connected account, verify posted source evidence, filters/hidden/split representations, pending replacement and available documented recovery first. A specifically authorized manual correction can proceed without feed takeover when the operation's effects are known. Save its source identity, inserted app IDs, cutoff and duplicate checks, then open a `manual-repair-watch` case for possible later feed arrival. A later match creates a new deduplication proposal; it does not authorize deleting either row. Use the chosen manual-account balance option explicitly. Current-balance correction is not historical reconciliation; require a verified baseline for backfill against opening adjustments.

Reversals are new changes against current state, not blind replay of snapshots. Preserve verified independent changes after partial failure. Finish with verified, unapplied and unknown operations, residual differences and evidence links. A future check is only scheduled when an authorized scheduler returns a real handle; otherwise the case remains pending for the next run.
