# Explain what happened to money

**Before starting:** Apply the [setup prerequisite](../along-sync-account/references/workflow.md#explicit-setup-and-account-actions). If setup is missing or partial, ask the user to run `$along-setup` and stop this workflow.

Produce a read-only answer or private report from existing evidence, authorized app observations or supplied exports. A report does not require a full reconciliation and does not edit transactions, categories, tags, budgets, goals or app settings. It does not establish investment performance or retirement forecasts. Read [workflow](../along-sync-account/references/workflow.md) and [analysis basis](../along-sync-account/references/analysis.md). Read [records](../along-sync-account/references/records.md) before saving. When interpreting app-specific fields or goal and budget behavior, read [capabilities](../along-sync-account/references/capabilities.md) and [Monarch knowledge](../along-sync-account/references/monarch.md); if a required reference is missing, stop that dependent interpretation and report the gap.

Use [along-plan-cash](../along-plan-cash/SKILL.md) for future bills, recurring obligations or account-level liquidity. Use [along-manage-budget](../along-manage-budget/SKILL.md) when the user wants to change a budget, rollover, allocation or goal funding. Use [along-reconcile](../along-reconcile/SKILL.md) when the question requires proving source completeness or correcting records.

## Answer the question

1. Resolve the household, account or owner scope, exact period(s), timezone, currency and requested measure. For an unspecified historical period, state the last complete calendar month as the default. Define “spending,” “cash movement,” “income,” “savings” and “budget variance” using the shared analysis basis; do not treat them as interchangeable. Ask only when a missing choice materially changes the result, and provide supported independent findings while a non-decisive question remains open.

2. Select sufficient evidence and preserve provenance, coverage and observation dates. Reuse normalized records and reconciliation outcomes; check overlapping exports and stable account mappings. An app-only export can support an app-based report without proving source completeness. A supplied file can support a file-based report without a current bank login, after household setup. Fetch only an in-scope gap through the shared [evidence procedure](../along-sync-account/references/evidence.md); do not turn a narrow report into an all-account audit. Missing coverage is not zero activity.

3. State inclusion rules before aggregation: accounts, owners, date field, categories, tags, exclusions, pending treatment and accounting basis. Apply explicit AND/OR/NOT logic to observed fields. A known empty tag set differs from an unavailable tag column; an unavailable field leaves that filter unresolved. Preserve original values and user categories. Any analytical reclassification is labeled separately with its rationale and effect on totals, never written back as an app correction.

4. Keep household ownership and cost allocation separate. An owner scope describes the transaction or account owner when that field is actually observed. A cost allocation distributes a shared household expense or budget amount by an explicit preference; it does not create a private account, private budget or privacy boundary. If the app exposes one household budget, report that native budget as shared. Do not claim native private budgets unless the capability map and live observation establish one. Show the household total and analytical allocations separately so a $100 shared purchase remains $100 of household spending even when a local view assigns $50 to each person.

5. Compute requested totals, contributors and comparisons with traceable row references, following [analysis basis](../along-sync-account/references/analysis.md). Treat split allocations and their parent once. Use comparable periods and coverage. Label month-to-date versus full-month comparisons; calculate percentage change only with a meaningful denominator, and report an absolute difference when the baseline is zero. Keep currencies separate unless a supported, disclosed conversion is requested. Preserve pending items separately from posted activity.

6. For budget comparisons, identify the exact historical budget version, period, budget type, group/category scope, rollover semantics and expense/refund basis applicable to each period. Compare actuals with the compatible plan, keeping original monthly values and later revisions distinguishable. Do not substitute today's budget for historical history. A current-budget scenario is allowed only when explicitly requested and must be labeled as such. If a version or rollover history is unavailable, mark that comparison unavailable and finish supported actuals and other comparisons.

7. For goals, distinguish budgeted allocation, evidenced funding or transfer, goal-linked expense treatment, and refund or reimbursement. A goal-funded purchase may affect a budget and a goal view differently; follow the observed app capability and the household accounting basis rather than counting a transfer as spending. Keep refunds tied to the original purchase or allocation when evidenced, including partial and cross-period refunds. An expected refund is not historical cash until it is observed. If native goal linkage is unsupported or unclear, report the local analytical relationship and limitation without claiming an app link.

8. For “why did cash change?”, bridge comparable opening and closing cash balances with observed cash movements on their cash dates. Distinguish card and loan repayments and transfers across the selected cash boundary from purchase spending. Expose missing counterparts and any unexplained residual; a balancing plug is not an explanation. Investment valuation changes are not reconstructible from deposits and withdrawals alone.

9. Lead with the answer and largest supported drivers. Include period, scope, basis, source and coverage limits, and a small table or visual only when it improves understanding. Make underlying transactions and inclusion rules available as evidence. Describe observed contributors separately from inferred reasons; amounts alone do not prove intent or causation. For a savings-rate request, state the numerator and denominator and distinguish take-home surplus from gross-pay savings; absent paystub components cannot be inferred from deposits. Goal or payroll observations can inform an explanation without claiming those systems were reconciled. If the user asks for an action, hand the result to `along-manage-budget`, `along-plan-cash` or `along-reconcile` rather than silently changing the report's read-only mode.

## Save and finish

Follow [saved analysis](../along-sync-account/references/analysis.md#saved-analysis) when persisting a report. Save the query and basis, input references, inclusion/exclusion decisions, ownership and analytical allocation views, calculation references, historical budget-version references when used, goal/refund relationships, results and residuals. Preserve source values and the version used; a report is a derived view, not a standing budget, obligation or transaction registry.

Check that components sum to totals, account identities are not counted twice, split parents are not added to children, refunds follow the stated basis, cost allocations reconcile to the household total when they are intended to, and differences or residuals are reproducible. Completion means every requested measure has a supported result or explicit gap for the stated evidence scope. A report generated successfully does not upgrade evidence to reconciled or current.
