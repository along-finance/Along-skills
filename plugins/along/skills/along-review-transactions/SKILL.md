# Review household transactions

Treat this as a queue over the finance-app ledger. It completes transaction decisions and authorized app metadata; it does not establish that the source feed is complete. Route source comparison, missing or duplicate recovery, balance discrepancies and cross-account matching to [along-reconcile](../along-reconcile/SKILL.md).

Read [workflow](../along-sync-account/references/workflow.md) for every run; [records](../along-sync-account/references/records.md) when reading or saving household evidence/cases; [capabilities](../along-sync-account/references/capabilities.md) before interpreting unfamiliar app behavior; and [changes](../along-sync-account/references/changes.md) before proposing or applying app changes. Read [categorization](references/categorization.md) for every review. Read [splits and tenders](references/splits-and-tenders.md) for receipt-backed allocations, [refunds and reimbursements](references/refunds-and-reimbursements.md) for credits or expected repayments, and [review state and rules](references/review-state-and-rules.md) for native reviewed flags, assignments or rule work. Before acquiring source evidence, read the shared [evidence](../along-sync-account/references/evidence.md) contract; before mailbox access read [email](../along-sync-account/references/email.md); before interpreting Monarch behavior read [Monarch knowledge](../along-sync-account/references/monarch.md).

## Review loop

1. **Set the queue.** Resolve the household, app workspace, target account or owner scope, timezone, period, as-of point and mode. “Review new transactions” means the saved review cursor plus newly observed or changed rows; include pending-to-posted replacements and rows whose app identity changed. If no cursor exists, state a latest-seven-days scope, following the shared date policy. Use actual creation/change cursors when available; posted dates alone can miss late-arriving old transactions. If the app lacks a change feed, inspect the scoped native Needs Review queue and compare saved identities, and disclose any older-change coverage limit. An explicit period or transaction list wins and must not be widened silently. Default review/check requests to `inspect`; categorization, splitting or fixing may produce `prepare`, and a precise request for fixed records and exact values may authorize `apply` under the changes contract.

2. **Reinspect identity and state.** Confirm the selected app account, ownership, feed state and relevant ledger before reading or writing. Load saved preferences, prior dispositions and unresolved cases. Map source identities, app rows, replacement rows, split parents and allocation children; parent and child identities are related by the map and are not required to share one row ID. Preserve deliberate user edits and do not treat a merchant name as purpose evidence.

3. **Build dispositions.** Group rows into already-resolved, needs category/context, receipt or split, credit/refund/reimbursement, transfer/payment, review-state or assignment, rule candidate, and source-completeness handoff. Ask focused questions for only the rows that need them. Keep unresolved items and partner-assigned questions in the private queue so the next run can resume them; do not duplicate ledger rows in the queue.

4. **Classify with evidence.** Reuse actual category identifiers and household conventions. Distinguish spending from internal transfers, card payments, loan principal, interest, fees, refunds, reversals, rewards, store credit and reimbursements. For a receipt or user context, use the exact arithmetic in [splits and tenders](references/splits-and-tenders.md). For one or more credits or repayments, use the many-record allocation and lifecycle rules in [refunds and reimbursements](references/refunds-and-reimbursements.md). Evidence can support a proposal without proving source completeness; escalate that question to `along-reconcile`.

5. **Preview native work.** For marking rows reviewed, assigning them, or changing a rule, read [review state and rules](references/review-state-and-rules.md). Show the fixed transaction IDs or predicate, current and proposed values, affected historical/future rows, precedence or side effects, and reversibility. A single ambiguous answer does not justify a merchant-wide rule. A recurring rule needs explicit user intent; an inferred batch needs a proposal and approval. If capability or side effects are unknown, prepare only.

6. **Apply only the bounded change.** Use the shared single-writer, snapshot, live-drift, journal and reread protocol. A precise user request can authorize its exact listed operations; a broad request such as “clean up this week” authorizes review and proposal, not an unseen bulk mutation. Treat reviewed state, assignment, category, split, rule, exclusion and ledger repair as separate operations with their own capability and approval checks. Native splitting can change review state or create allocation children; include that effect in the proposal and verify it rather than assuming the parent row stayed identical.

7. **Close the run.** Reopen changed rows and verify values, review state, assignment, split totals, rule scope and affected relationships. Persist the run, dispositions, evidence and unresolved cases; advance the review cursor only over the requested observed scope, and retain references to source/app records rather than copying them into a competing ledger. Report reviewed, categorized, split, assigned, rule-previewed, unresolved and handed-off counts separately. `complete` means every row in the stated queue has a disposition and every applied change is verified; missing evidence or unknown app behavior makes the relevant result `partial` or `blocked`.
